# INT-074: Transparent construction UX contract

## Intent interpretation

Issue #74 turns the product invariant "Nothing happens under the rug" into an implementation-ready UX and architecture contract before #75-#78 mutate the product experience.

The work is documentation/architecture, not runtime implementation. It must produce:

- `docs/product/TRANSPARENT_PROGRAMMING_UX.md`
- an ADR for observable construction/execution
- wireframe-level or Mermaid flows that make implementation possible without private context

## Source facts

- Parent epic #64 defines transparency as: intention -> proposed program change -> accepted program -> current instruction -> runtime state transition -> visible result.
- `AGENTS.md` says AI proposes, learner decides, runtime proves, and no AI-originated program mutation may enter accepted state invisibly.
- `LEARNER_JOURNEY.md` requires generated code to stay visible and AI proposals to remain provisional until learner decision.
- `SYSTEM_DESIGN.md` separates the AI proposal path from deterministic runtime execution.
- `PROGRAMMING_MODEL.md` defines canonical program as the source of truth; visual blocks and text are projections.
- `DESIGN_SYSTEM.md` defines proposal, accepted code and runtime evidence as distinct visual states.
- `INTERACTION_MODEL.md` requires touch-first, no-drag editing paths and Action Palette affordances.
- `CROSS_SURFACE_COMPATIBILITY.md` requires identical semantics across Web/Tablet and Studio.

## Product decision proposed for construction

The transparent programming contract should define one semantic state machine shared by Web/Tablet and Studio, with surface-specific affordances only at the presentation layer.
