# Intent interpretation

Issue #119 defines Agorix Worlds as the shared narrative and visual layer for missions.
Worlds motivate the learner through setting, characters, objectives, animation and feedback,
but they do not own programming semantics, runtime semantics or canonical program state.

The implementation should produce a durable product architecture document for Worlds and
prepare a narrow first slice that the current Web surface and future Studio World Preview
can share.

## Source facts

- Parent epic: #116, Agorix Experience & Surface Architecture.
- Required deliverable: `docs/product/WORLDS.md`.
- Required boundaries: World -> Mission contract -> Canonical Program + Runtime.
- Existing architecture: canonical program, runtime, curriculum and stage contracts are shared
  across surfaces.
- Existing design language: product chrome stays calm; Worlds carry richer visual delight.
- Existing interaction model: Web is touch-first and no-drag-required for the First Mission.

## Proposed interpretation

- Treat `runtime/src/world.ts` as the generic execution state, not as the product/theme
  architecture named "Agorix Worlds".
- Define Worlds as a content/theme contract attached to missions by stable IDs.
- Keep mission IDs and completion predicates locale-independent.
- Allow localized visual/narrative assets through catalog entries, not through runtime forks.
- Specify one starter world for the current First Mission without adding a generic game engine.
